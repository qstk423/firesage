# 三、完整请求链路：你必须能脱稿画出来

入口：

```text

  → POST /api/ask
  → backend/main.py:ask()

  → Pipeline._ask()                主状态机
```

主状态机：

```text
输入检查
  → scene.structure()              场景结构化
  → intent.route()                 意图分流
  → risk.assess()                  风险等级
  → 查询改写/复合问拆分
  → HybridRetriever.retrieve()
      ├─ BM25
      ├─ bge-m3 向量召回
      └─ GraphRAG
  → RRF 融合
  → 法规规则重排 + CrossEncoder
  → CRAG 证据质量判断
  → LLM 结构化生成
  → verifier.verify()
  → 返回回答、引用、图谱路径、阶段和追问
```

快速观察真实链路：

```bash
cd backend
python3 scripts/trace.py "楼道堆放杂物违反什么规定"
python3 scripts/trace.py
```

不带参数会跑正常法规、真火情、库外法规、闲聊和宽问五类问题。

## 检索前可能直接结束的分支

- 无效或乱码输入：拒答
- 点名知识库外法规或主题：范围拒答
- 真火情：直接给应急指引，不检索
- 非消防问题：拒答
- 闲聊：引导用户问消防问题
- 关键要素缺失：澄清追问

答辩时可以这样概括：

> 传统 RAG 默认所有输入都值得检索和回答；FireSage 先判断“该不该答、现在该答什么”，
> 再判断“有没有足够证据”，最后才让模型组织语言。

# 四、数据层：理解“句找条答”

当前真实规模：

```text
10 部法规
524 个条款
1675 个语义句
118 个图谱实体
972 条图谱关系
229 道 FireEval 题
```

## 为什么不直接固定长度切割

固定长度切割可能把一条法律条文从中间切断，引用时既不完整，也难标明条号。

FireSage 采用两级单位：

- 条款是引用和回答的完整单位
- 语义句是检索的细粒度单位
- `parent_id` 把语义句映射回所属条款
- 同一条款有多个句子命中时，按最高分聚合

你可以用 Transformer 知识解释：

> 一整条长法条直接编码容易发生语义稀释；句级编码提高局部语义匹配，
> 但最终证据又必须保持法律条款完整，所以检索粒度和引用粒度被有意解耦。

这就是“句找条答”。

# 五、三路召回：每一路解决什么错误

## 1. BM25

核心价值不是“老算法”，而是精确词项匹配：

- 条款号、罚款金额、机构名称
- 法律固定表述
- 精确关键词

`k1` 控制词频饱和，`b` 控制文档长度归一；`b=0` 表示不考虑长度。

BM25 的弱点是词汇鸿沟：

```text
用户：楼道堆纸箱
法条：占用疏散通道
```

字面重合很少，可能漏召回。

## 2. bge-m3 语义向量

解决生活口语与规范法言法语之间的语义映射。

双塔模型把 query 和 document 分别编码，因此：

- 文档向量可离线建立索引
- 在线只编码 query，速度快
- 适合大候选集召回
- 但细粒度交互弱，对条号和数字不如 BM25

## 3. GraphRAG

解决关系型问题并提供可解释路径，例如：

```text
违规行为:占用疏散通道
  → 处罚
  → 处罚主体
  → 依据条款
```

它不是“让图谱代替向量库”，而是第三路召回信号。

图谱价值有两个：

1. 关系召回：适合“谁负责、怎么罚、有哪些义务”
2. 可解释性：能展示实体—关系—条款路径

# 六、RRF：你要真正掌握的第一个算法点

三路原始分数不能直接相加：

- BM25 分值没有固定上界
- 余弦相似度通常在有限区间
- 图谱分数是自定义量纲

RRF 只使用排名：

```text
RRF(article) = Σ weight_channel / (K + rank_channel)
```

项目参数：

```text
RRF_K = 60
BM25 0.42 / Vector 0.33 / Graph 0.25
```

向量模型降级时：

```text
BM25 0.72 / Vector 0.10 / Graph 0.18
```

## K 的直觉

- K 越小：头部名次差异越大，单路第一名影响更强
- K 越大：名次差异被压平，更强调多路一致性
- K=0：第一名和第二名贡献差距过大，容易被单路异常结果带偏
- K 极大：不同排名几乎没有区别，排序信号被稀释

## 动手任务

不使用 `rank_bm25`、sklearn 或 LangChain，手写一个最小 BM25 和 RRF。
语料使用 `backend/data/chunks.json`。

通过标准：

- 对三个问题输出 top-5
- 能打印每一路 rank 和最终 RRF 分
- 手写 BM25 的 top-3 与项目结果有明显重合
- 能解释权重和 K 变化后的排序

# 七、为什么召回后还要 CrossEncoder

这是标准的两阶段检索：

## 第一阶段：高召回

BM25、向量和图谱快速找出候选，目标是尽量别漏。

## 第二阶段：高精度

CrossEncoder 把 query 与候选条款拼接后共同编码，直接输出相关性分数。

相较双塔：

- 双塔快，可预计算，适合召回
- CrossEncoder 慢，不能为所有文档在线计算
- CrossEncoder 有 token 级交互，少量候选上更准确

项目模型：

```text
向量召回：BAAI/bge-m3
CrossEncoder：BAAI/bge-reranker-v2-m3
```

答辩标准句：

> 双塔负责从全库中快速缩小范围，CrossEncoder 负责对少量候选精确比较，
> 用“召回求全、精排求准”平衡速度和效果。

# 八、意图路由：这里最容易把“微调”说错

四个类别：

```text
law / emergency / refuse / chitchat
```

实际分类器：

```text
字符级 2–4 gram TF-IDF
+ LogisticRegression
+ class_weight="balanced"
```

训练规模：

```text
157 条
law 122 / emergency 18 / refuse 11 / chitchat 6
```

同一 test 集结果：

```text
纯规则  0.9062
纯模型  0.9375
hybrid  0.9688
```

## hybrid 的真实执行顺序

1. 安全拒答规则
2. 明显库外主题
3. 明显法规咨询
4. 强火情信号
5. ML 分类器，最低置信度 0.42
6. 模型无结论时退回规则

为什么不是纯模型：

- emergency 训练样本只有 18 条
- 安全硬约束不能完全交给概率模型
- 规则保证高风险边界，模型补足口语泛化
- 0.9688 的对比结果支持 hybrid

## 严谨口径

可以说：

> 我们训练了消防领域意图分类器，并以规则与模型混合方式上线。

谨慎说：

> 项目完成了意图路由微调实验。

不要说：

> 我们微调了一个消防大模型。

TF-IDF+逻辑回归是传统监督分类器训练，并不是 Transformer 参数微调。
如果评委技术背景强，混淆两者会直接伤害可信度。

## 为什么没用 BERT

- 只有 157 条训练样本，复杂模型过拟合风险高
- 任务是四分类，字符 n-gram 已能覆盖大量消防关键词和口语变体
- CPU 可训练、可离线部署、推理延迟低
- 实验结果已经达到当前需求

同时主动承认：样本少、类别不均衡、test 只有 32 条，0.9688 仍需更大测试集验证。

# 九、风险、意图和证据可信度是三件不同的事

这是答辩中很有价值的区分。

## 意图

用户想做什么：咨询法规、求助火情、闲聊或问库外问题。

## 风险

现场严重程度：紧急、高、中、低。风险在检索前判断。

## 证据可信度

检索结果是否足以支持回答，由 CRAG 判断：

```text
Correct / Ambiguous / Incorrect
```

三者不能混为一谈：

- “家里着火了”风险高，直接应急分流
- “楼道堆杂物怎么处罚”是法规意图，可能风险中等
- 即使问题风险高，如果知识库证据不足，也不能编答案

CRAG 关键阈值：

```text
Ambiguous 0.22
Incorrect 0.12
CrossEncoder floor 0.50
图谱命中时 soft floor 0.47
```

阈值升高：回答更谨慎、拒答或引导更多、覆盖率下降。
阈值降低：覆盖更多，但错误回答风险上升。

# 十、结构化生成与独立核验

LLM 输出五个字段：

```text
conclusion / conditions / basis / supplement / confidence
```

结构化输出的价值：

- 前端展示稳定
- 核验器容易定位依据和金额
- 失败时可针对问题重新生成
- 便于离线评测

## 核验器五条规则

1. 回答引用的条款必须在本次检索依据中
2. 罚款金额必须在依据原文中存在
3. 单位和个人等处罚主体必须匹配
4. 普通建筑问题不能仅引用高层专项规定
5. 问处罚时，依据中必须包含处罚条款

## 失败后的三级处理

```text
第一次核验失败
  → 将 issues 作为 feedback 重新生成一次

第二次仍失败
  → 弃用 LLM 文本，使用抽取式原文回答

检索证据本身不足
  → 在生成前就引导或拒答
```

为什么不用 LLM 自检：

> 让模型检查自己的事实错误，相当于让它自证清白。
> 规则核验可解释、可单测、可复现，也没有额外推理成本。

## 你的第一个代码练习

`verifier.py::_extract_cited_articles()` 当前存在交叉配对缺陷：

```text
《消防法》第二十八条
61号令第二十一条
```

旧逻辑可能错误组合成：

```text
消防法·第二十一条
61号令·第二十八条
```

根因是“法规名是否出现”和“条号是否出现”被全局独立判断，
没有检查两者在同一引用局部内相邻。

任务：

- 自己修改引用抽取逻辑
- 为两部法规、两个条号的交叉场景写单元测试
- 再跑 `scripts/trace.py`
- 证明错误降级消失

这是最适合你接管项目的第一处真实缺陷。

# 十一、评测闭环：这是你与教程 RAG 的主要差距

FireEval v1 共 229 题：

```text
train 160 / dev 34 / test 35
```

题型：

```text
生活化口语 57
直接法规查询 47
处罚与责任主体 37
跨条款综合 26
多轮追问 22
应急 15
知识库外消防 15
非消防 10
```

后面三类共 40 题，正确行为往往不是正常回答。

## 指标

- Hit@1：第一个结果是否命中任一正确条款
- Hit@3：前三个结果是否命中
- MRR：第一个正确结果排名倒数的均值

## 当前消融结果

| 模式 | Hit@1 | Hit@3 | MRR |
|---|---:|---:|---:|
| BM25 | 0.6098 | 0.8659 | 0.7415 |
| BM25 + Vector | 0.7256 | 0.9268 | 0.8254 |
| Hybrid，无重排 | 0.5732 | 0.8902 | 0.7308 |
| Full，三路 + 重排 + CE | **0.9024** | **0.9756** | **0.9394** |

## 必须主动解释的异常

Hybrid 加入图谱后反而比 BM25+Vector 差。

正确解释：

> 图谱按关系扩展会提高候选覆盖，同时引入“关系相关但主题不够精确”的条款。
> 没有重排时，这些噪声可能挤掉 top-1；加入法规规则重排和 CrossEncoder 后，
> 噪声被压低，图谱的覆盖收益才释放。因此图谱与重排应视为组合模块。

不要说“加任何模块都会涨分”。实验明确显示不是。

## 你必须亲自完成的实验

1. 跑 `python3 backend/scripts/ablation_retrieval.py`
2. 手算一题的 Hit@1、Hit@3、MRR
3. 修改通道权重并重跑
4. 找出最明显的掉分类别
5. 改回权重，确认结果恢复

做到这一步，你才真正拥有这些指标，而不是背别人的数字。

# 十二、训练相关产物：答辩口径必须分三层

## 1. 已训练并默认使用：意图分类器

```text
TF-IDF + LogisticRegression
模型文件：intent_clf.joblib
线上：hybrid
```

这是目前最扎实的训练成果。

## 2. 已训练但默认关闭：ML 重排器

训练数据：

```text
627 个 query-document pair
正样本 175 / 负样本 452
```

对比结果：

```text
dev：规则 0.9130 → 加 ML 0.8696（下降）
test：规则 0.6667 → 加 ML 0.7083（上升）
```

因此 `rag/rerank_ml.py` 中默认关闭，只有设置 `RERANK_ML=1` 才启用。

这不是失败，而是正确工程决策：

> 小数据上的收益不稳定，不能因为 test 有提升就忽略 dev 回退并贸然上线。

## 3. 已准备数据和脚本，但不能声称已上线：生成式 LoRA

SFT 数据：

```text
train 139 / dev 29 / test 32
格式：instruction-input-output JSONL
```

仓库里有 `build_gen_sft.py` 和 `train_gen_lora.py`，表示训练路径已准备。
除非能展示训练日志、adapter 权重、基座模型、显存配置和独立评测，
否则应说“已准备生成式 SFT/LoRA 实验”，不能说“生成模型已完成微调并上线”。

## 最稳妥的完整答法

> 项目训练并上线了轻量意图分类器；训练过实验性 ML 重排器，
> 但由于 dev/test 收益不一致默认未启用；同时准备了生成式 LoRA 的
> 200 条 SFT 数据和训练脚本，目前不把它作为线上能力宣传。

这比笼统说“我们做了大模型微调”更专业。

# 十五、你的答辩核心叙事

不要按文件列表讲，要按风险讲：

## 1. 问题

通用大模型在消防法规中可能编条款、编罚款，传统单路 RAG 仍可能召回错误证据。

## 2. 解法

检索前用意图和风险分流；中间用三路召回、RRF 与 CrossEncoder；
生成后用独立核验；证据不足则引导或拒答。

## 3. 证据

FireEval 229 题；Full 检索 Hit@1 0.9024；意图 hybrid 0.9688；
同时通过消融承认图谱无重排时是负收益。

## 4. 边界

原型阶段，知识库 10 部法规；意图数据仅 157 条；
ML 重排默认关闭；生成 LoRA 尚未作为线上能力；输出仅供辅助参考。

## 5. 价值

不是让模型更会说，而是让每个结论有出处、错误有拦截、能力有边界。

# 十六、模拟追问

## 为什么不用纯向量 RAG？

法条号、金额和固定术语需要精确匹配；生活口语需要语义匹配；
责任与处罚关系需要图谱。三者互补，并由重排压制噪声。

## 为什么不用 LangChain 直接搭？

可以用来搭主干，但本项目需要显式控制安全分流、每路分数贡献、
CRAG 判定、引用核验和逐级降级。直接实现使各层可观测、可单测、可消融。

不要说“LangChain 不好”，而要说“抽象层不完全符合本项目的可控与评测要求”。

## 微调了什么？

默认上线的是 TF-IDF+逻辑回归意图分类器，严格说是轻量领域分类器训练；
ML 重排器训练过但默认关闭；生成式 LoRA 已备数据和脚本，尚不作为线上能力。

## 既然图谱让 Hybrid 掉分，为什么还保留？

它扩大关系型问题的候选覆盖并提供解释路径；负收益来自缺少重排，
Full 结果证明图谱与重排结合后整体效果最高。

## 为什么不用 LLM 做所有判断？

安全分流和事实核验需要确定性、可解释和可测试。
概率模型适合补泛化，不适合独占高风险决策。

## 阈值怎么确定？

在 dev 集上平衡覆盖率与错误风险，并通过 test 与人工案例复核。
阈值升高更保守，降低则回答更多但误答风险上升。

注意：如果项目没有保存完整阈值搜索记录，不要声称做过复杂网格搜索。

## 当前最大的技术局限？

数据量小、类别不均衡；评测集仍是自建；法规覆盖有限；
核验器以规则为主，对复杂语义蕴含的检查能力有限。
