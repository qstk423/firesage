# FireSage v1.0 工程化路线

> 基线版本：v0.9.0（冻结，不修改）。开发分支：`v1.0-dev`。
> 产品范围：桌面端消防法规可信问答，不开展手机端。

## 指标口径

| 层级 | 指标 | v1.0 目标 |
|---|---|---:|
| 检索 | Recall@5 | ≥ 95% |
| 检索 | MRR | ≥ 0.85 |
| 生成 | 金标法规名+条号命中率 | ≥ 85% |
| 安全 | 库外正确拒答率 | ≥ 95% |
| 安全 | 无依据引用率 | 0 |
| 性能 | 检索 P95（Windows CPU） | ≤ 1.5s |
| 性能 | TTFT P95（RTX 4060） | ≤ 5s |
| 性能 | 常规回答总耗时 P95 | ≤ 15s |

“端到端契约通过率”和“严格金标通过率”必须分别报告，禁止用格式通过率代替问答准确率。

## 阶段一：可观测与严格评测

- 每次请求记录路由、查询准备、BM25、向量、图谱、融合、规则重排、
  CrossEncoder、模型生成、核验与重试耗时。
- 检索报告输出 Hit@1/3/5、MRR、P50/P95/max。
- 严格评测同时核对法规名和条号，避免不同法规同号条款误判。
- Windows 生成的报告提交到 `backend/eval_reports/`，报告不得包含密钥或模型权重。

完成条件：能够用一份报告明确回答“慢在哪里、错在哪里”。

## 阶段二：检索性能与质量

按 Windows 报告选择优化，不预设瓶颈：

1. 若 BGE 编码占比最高：A/B 测试 PyTorch、ONNX INT8、OpenVINO INT8；
2. 若 CrossEncoder 占比最高：对比候选数 3/4/6 的速度与 Recall@5；
3. 若多查询放大耗时：仅对复合问题启用子查询，普通问题保持单查询；
4. 加入查询向量与检索结果缓存，缓存键包含知识库版本；
5. 对法规名、主体、场所增加元数据过滤，提升同条号法规的区分度。

任何优化只有同时满足“速度提升、严格指标不下降”才合并。

## 阶段三：生成服务

- 保留 LoRA v2、五层守卫和两级核验；
- 对比 Transformers 与合并量化后的 GGUF/llama.cpp 推理；
- 量化后重跑严格评测，验证引用与拒答没有退化；
- 高频问法采用带知识库版本的结果缓存；
- 增加并发队列、超时、健康检查和优雅停止。

## 阶段四：可交付部署

- 发布独立 LoRA adapter 包、SHA256、模型卡和精确复现命令；
- 区分代码版本、语料版本、索引版本、基座版本和 adapter 版本；
- 保留 DeepSeek 云端回退链路；
- 提供 Windows 本地部署和 Linux 服务器部署；
- 加入 API 鉴权、限流、结构化日志和审计保留策略。

## 阶段五：盲测与发布门禁

- 建立 100～200 道未参与开发调参的盲测题；
- 覆盖法规问答、口语表达、复合问题、库外问题、应急问题与对抗输入；
- 测试集冻结后只由评测脚本读取，不根据单题结果写规则特判；
- 未达到本页指标时不得发布 v1.0.0，继续留在开发分支。
