# 消安智答 FireSage · 团队讲义（从零讲起）

> 读者：三名队员。假设你学过机器学习，知道传统 RAG 是「检索 → 拼进提示词 → 生成」。
> 不假设你了解本项目任何细节。
>
> 目标：读完这份讲义 + 亲手跑一遍 `scripts/trace.py`，你能独立讲清这个系统的每一层。

---

## 0 · 先建立一个总判断

传统 RAG 的目标是**答得好**。这个项目的目标是**答错要能被拦住**。

这句话是理解全部设计的钥匙。消防法规场景里，一个自信但错误的答案比"我不知道"危险得多——
基层人员照着错误条款去整改，出了事是要担责的。所以这个系统里有大量
传统 RAG 没有的东西：拒答、澄清、引导、核验、降级。这些不是锦上添花，是主线。

如果你只记住一句话：**我们宁可拒答，不可答错。**

## 1 · 传统 RAG 和这个项目差在哪

你熟悉的传统 RAG：

```
问题 → 向量检索 top-k → 塞进 prompt → LLM 生成 → 输出
```

这个项目：

```
问题 → ①意图分流 → ②三路检索 → ③置信判定 → ④生成 → ⑤核验 → 输出
         ↓拒答/应急      ↓RRF融合      ↓引导/拒答        ↓失败重生成/降级
```

多出来的五件事，逐个说明为什么必须有：

| 多出来的 | 传统 RAG 会怎样 | 为什么必须有 |
|---|---|---|
| ①意图分流 | 「家里着火了」也去检索法条 | 应急场景要立刻给逃生指引，不是给你念法律 |
| ②三路检索 | 只有向量一路 | 法条里大量精确术语，纯向量召不准；关系型问题需要图谱 |
| ③置信判定 | 检索不到也硬答 | 证据不足时必须拒答或引导，不能编 |
| ④结构化生成 | 自由文本 | 要固定输出「结论/适用条件/法规依据/补充说明/可信度」 |
| ⑤核验 | 无 | 检查回答引用的条款、金额、主体是否真的在依据里 |

**第⑤条是最没有现成轮子、也最值钱的一环。** 记住它。

## 2 · 全景：一个问题进来会发生什么

别背文字，直接看真实执行路径。项目里有一个显微镜工具：

```bash
cd backend
python3 scripts/trace.py "楼道堆放杂物违反什么规定"   # 单个问题
python3 scripts/trace.py                              # 5 个对照样例
```

它打印每一步调用了哪个函数、在哪个文件第几行、产出了什么。
文件名和行号是从 `__code__` 实时读出来的，代码改了它也不会说谎。

**每个人第一件事就是跑它，尤其跑不带参数的 5 个样例**，你会直接看到
应急、拒答、闲聊、宽问分别在第几步就拐弯了，比读十页文档管用。

主流程代码在 `backend/rag/pipeline.py` 的 `Pipeline._ask()`。
这一个函数就是整个系统的骨架，其余文件都是它调用的零件。

## 3 · 数据层：知识库是怎么来的

### 3.1 规模（**以下数字为准，旧材料里的都过时了**）

| 项 | 值 | 怎么查证 |
|---|---|---|
| 法规来源 | 10 部 | `rag/graphrag.py` 的 `SOURCE_FILES` |
| 条款数 | 524 | `chunks.json` 里 `article` 字段去重 |
| 语义句 | 1675 | `chunks.json` 的记录总数 |
| 图谱实体 | **118** | `graph.json` 的 `nodes` |
| 图谱关系 | **972** | `graph.json` 的 `edges` |
| 评测集 FireEval v1 | 229 题 | `eval/fireeval_v1.json` |

10 部法规：消防法、61 号令、高层规定、责任制办法、39 号令、
电动车充电、密集场所、广东高层、技术服务、消设审查。

图谱实体类型分布：消防对象 30 / 主体 29 / 违规行为 22 / 管理义务 22 / 处罚 7 / 主题 6 / 政府职责 2。
关系类型分布：涉及 654 / 义务 178 / 处罚 78 / 责任 43 / 禁止 19。

### 3.2 为什么不按固定长度切块

你们做传统 RAG 习惯 `RecursiveCharacterTextSplitter(chunk_size=500)`。这里不行。

法条的最小语义单位是**条款**，切断了就没法引用。所以采用两级结构：

- **条款级**：一条法条 = 一个引用单位，共 524 条。回答里引用的就是它。
- **语义句级**：把条款再切成句子，共 1675 句。检索时用它。

检索用句、回答引用条款，中间通过 `parent_id` 关联。
代码里叫「句找条答」：句子级召回后，按条款取最高分聚合（`semantic_index.py`）。

**为什么这样做**：条款往往很长（几百字），整条做向量会稀释语义；
但引用又必须精确到条。拆开检索、聚合引用，两头都要。

## 4 · 检索层（三路 + 融合 + 精排）

代码：`backend/rag/retriever.py`

### 4.1 第一路 BM25

给学过 ML 的人一句话：**BM25 就是 TF-IDF 的改良版**，多了两件事——
词频饱和（一个词出现 20 次不比出现 5 次强多少）和文档长度归一。

两个超参：`k1` 控制词频饱和速度，`b` 控制长度归一强度（`b=0` 就是完全不归一）。

**为什么法规场景离不开它**：法条里全是「第二十八条」「五千元以上五万元以下」
这种精确串，向量模型对数字和专有名词不敏感，BM25 对它们最擅长。

### 4.2 第二路 语义向量

模型 `BAAI/bge-m3`，索引用 FAISS，代码在 `semantic_index.py`。

作用是覆盖 BM25 的盲区：用户说「楼道堆纸箱」，法条写「占用疏散通道」，
字面零重合，只有向量能连起来。

**工程细节值得注意**：模型加载失败时会自动降级为 TF-IDF 字符向量
（`semantic_index.py` 里有这段逻辑），保证系统永远不会因为模型问题整个不可用。
降级时通道权重也会切换成 `CHANNEL_WEIGHTS_DEGRADED`。

### 4.3 第三路 知识图谱

代码 `rag/graphrag.py`。从法条里抽实体和关系建图，例如：

```
主体:个人 --[义务]--> 管理义务:维护保养消防设施   (来自 消防法·第五条)
```

检索时从问题里识别实体，沿关系走，找到相关条款。
它的独特价值是**能给出"为什么找到这一条"的路径**，前端可以点邻居跳转，
这是纯向量检索给不出的可解释性。

### 4.4 RRF 融合：本项目最容易被追问的一点

三路各自给出一个排序，怎么合并？

**不能直接把分数相加**——BM25 分数可能是 12.7，余弦相似度是 0.83，
图谱分数是自定义的，三者量纲完全不同，相加等于让 BM25 独裁。

RRF（Reciprocal Rank Fusion）只看**排名**不看分数：

```
score(文档) = Σ  权重ᵢ / (K + rankᵢ)
```

代码在 `retriever.py`，`RRF_K = 60`，权重是：

| 通道 | 正常 | 向量降级时 |
|---|---|---|
| bm25 | 0.42 | 0.72 |
| vector | 0.33 | 0.10 |
| graph | 0.25 | 0.18 |

`K=60` 的作用是**压平头部差距**：没有 K 的话第 1 名和第 2 名分差是 1 vs 0.5（差一倍），
加了 60 就变成 1/61 vs 1/62（几乎相等），避免任何单路的第一名直接决定结果。

**补充一个知识点**：LangChain 的 `EnsembleRetriever` 内部用的就是 RRF，常数也是 60。
所以你们可能已经用过，只是没人告诉过你它叫什么。

### 4.5 精排：CrossEncoder

模型 `BAAI/bge-reranker-v2-m3`。

和检索用的双塔模型区别在于：双塔是把问题和文档**分别**编码再算相似度（快，可预先建索引）；
CrossEncoder 是把问题和文档**拼在一起**送进模型打分（慢，但准）。

所以流程是：三路先召回一批候选（快），再用 CrossEncoder 对少量候选精排（准）。
这是信息检索里的标准两阶段范式。

## 5 · 评测层（先讲这个，因为下一节要用）

代码在 `backend/scripts/`：`evaluate_fireeval.py`、`ablation_retrieval.py`、`gate_retrieval.py`。

评测集 `eval/fireeval_v1.json`，229 题，按 160/34/35 分成 train/dev/test。
题目类型分布：

| 类型 | 题数 |
|---|---|
| 生活化口语表达 | 57 |
| 直接法规查询 | 47 |
| 处罚与责任主体 | 37 |
| 跨条款综合问题 | 26 |
| 多轮追问 | 22 |
| 应急问题 | 15 |
| 知识库外消防问题 | 15 |
| 非消防问题 | 10 |

注意后三类共 40 题（占 17%）**根本不该被正常回答**——考的是应急和拒答。
这个设计本身就是亮点，可以主动讲。

指标：Hit@1（正确条款排第一的比例）、Hit@3、MRR（正确条款排名倒数的平均）。
学过 ML 的对这三个应该不陌生，就是标准排序指标。

### 消融表（务必人人会讲）

| 模式 | 说明 | Hit@1 | Hit@3 | MRR |
|---|---|---|---|---|
| bm25 | 仅 BM25 | 0.6098 | 0.8659 | 0.7415 |
| bm25_vector | BM25 + 向量 | 0.7256 | 0.9268 | 0.8254 |
| hybrid | 三路，不重排 | 0.5732 | 0.8902 | 0.7308 |
| full | 三路 + 重排 + CE | **0.9024** | **0.9756** | **0.9394** |

### ⚠️ 这张表里有个坑，必须提前准备答案

**`hybrid`（0.5732）比 `bm25_vector`（0.7256）还低。** 评委只要看得懂表就会问这个。

标准答法：

> 加入图谱这一路，在**没有重排**的情况下是负收益。原因是图谱按关系召回，
> 会带进来一批"关系相关但主题不精确"的条款，把 top1 挤掉了。
> 但它确实扩大了召回覆盖面。重排（法规意图重排 + CrossEncoder）的作用
> 就是把这批噪声压下去、同时保留图谱带来的覆盖增益——所以 full 的
> Hit@1 从 0.7256 跳到 0.9024。
> **结论是：图谱的价值必须靠重排才能释放，这两个模块是绑定的，不能只上一个。**

这个答法之所以有分量，是因为它**承认了一个中间步骤是负收益**，而不是宣称每加一层都涨分。
评委听得出真假。

## 6 · 分流层：意图路由与微调

代码：`rag/intent.py`（规则）、`rag/intent_ml.py`（加载模型）、`scripts/train_intent.py`（训练）。

### 6.1 四个意图

| 意图 | 处理方式 |
|---|---|
| `law` | 走完整检索问答 |
| `emergency` | 直接返回内置逃生指引，**不检索** |
| `refuse` | 拒答护栏 |
| `chitchat` | 引导到可问范围 |

### 6.2 模型本身（对 ML 背景的队员这段最好懂）

就是一个标准文本多分类：

- 特征：`TfidfVectorizer(analyzer="char_wb", ngram_range=(2,4))`——字符级 n-gram，
  中文不用分词，对错别字和口语鲁棒
- 分类器：`LogisticRegression`
- 产物：`data/models/intent_clf.joblib`

### 6.3 必背数字

| 项 | 值 |
|---|---|
| 训练集 | 157 条 |
| 标签分布 | law 122 / emergency 18 / refuse 11 / chitchat 6 |
| test 集 | 32 条（dev 29 条） |
| test 纯规则 | 0.9062 |
| test 纯模型 | 0.9375 |
| test **hybrid（线上）** | **0.9688** |

### 6.4 三个必答题

**问：为什么不微调 BERT？**
157 条样本，微调 BERT 必然过拟合；TF-IDF + LR 在 CPU 上秒级训练、毫秒级推理、
结果完全可复现。这是数据量决定的选择，不是能力问题。

**问：为什么线上用 hybrid 而不是纯模型？**
看数字——规则 0.9062、模型 0.9375、hybrid 0.9688，单独都不如合起来。
更重要的是：`emergency` 只有 18 条训练样本，把"家里着火了"这种命悬一线的判断
交给一个概率模型不负责任，所以强信号走规则硬保证，模型只负责补规则漏掉的口语表达。

**问：局限是什么？**（**主动说，别等着被问出来**）
样本量小（157 条）、标签严重不均衡（law 占 78%）、test 集只有 32 题所以指标有波动。
下一步是扩数据。承认这些比被追问出来强得多。

## 7 · 生成层

代码：`rag/llm.py` + `Pipeline._llm_structured` / `_extractive_structured`。

不要自由文本，强制结构化 JSON，五个字段：
`conclusion`（结论）、`conditions`（适用条件）、`basis`（法规依据）、
`supplement`（补充说明）、`confidence`（可信度）。

**关键设计：检索与生成解耦。** 事实全部来自检索到的条款原文，
模型只负责组织语言，不负责回忆法条。这是抑制幻觉的根本手段。

**降级路径**：没配 LLM key、或 LLM 没返回合法 JSON 时，
走 `_extractive_structured` 直接摘录原文。抽取式回答天然可信——
因为它就是原文，一个字都没改。系统因此永远有输出。

## 8 · 核验层（最值钱的一环）

代码：`rag/verifier.py` 的 `verify()`。

生成完不直接返回，先拿回答和依据条款逐项对照，五条规则：

| 规则 | 检查什么 |
|---|---|
| 条款存在性 | 回答引用的条款必须在本次检索结果里（防编造） |
| 处罚金额一致 | 回答里的罚款数额必须在依据原文中出现 |
| 处罚主体匹配 | 说"对单位处罚"，依据不能只讲个人 |
| 建筑适用性 | 非高层问题不能只拿高层专项规定当处罚依据 |
| 处罚意图覆盖 | 问处罚，依据里必须真的含处罚条款 |

**三级处理**（这个流程要能背）：

1. 核验失败 → 把失败原因作为反馈，**重新生成一次**
2. 再次失败 → **弃用 LLM 回答**，降级为抽取式原文摘录
3. 证据本身就不足 → 上游 CRAG 阶段已经引导或拒答了，走不到这里

CRAG 阈值在 `pipeline.py` 顶部：`CRAG_AMBIGUOUS = 0.22`、`CRAG_INCORRECT = 0.12`、
`CRAG_CE_FLOOR = 0.50`、`CRAG_CE_SOFT = 0.47`。

**问：为什么核验用规则代码，不让 LLM 自查？**
让模型检查自己等于让它自证清白，不可信；规则代码可解释、可单测、可复现，而且不花钱。

## 11 · 常见追问速查

| 追问 | 答法要点 |
|---|---|
| 为什么不直接用 LangChain？ | 主干等价，但要在检索前做安全分流、生成后做逐条引用核验，这两处都要改框架内部行为；而且手写的每层都能单独消融拿数字 |
| 为什么不用大模型直接答？ | 会编条款、编罚款数额，且无法追溯依据；我们把事实来源限定在检索结果里 |
| hybrid 为什么比 bm25+vector 低？ | 见 §5，图谱价值需靠重排释放，两模块绑定 |
| 微调了什么？ | 意图分类器（TF-IDF+LR），不是生成模型；因为分错路径的代价远大于答得不漂亮 |
| 157 条样本会不会太少？ | 会，主动承认；正因为少才没上 BERT；下一步扩数据 |
| 拒答会不会太保守？ | 评测集里专门有 40 题考拒答与应急；宁可拒答不可答错是消防场景的硬要求 |
| 图谱有什么用？ | 关系型问题的召回 + 可解释路径（能说清"为什么找到这一条"） |
| 怎么保证不宕机？ | 每层都有降级：向量模型挂了退 TF-IDF、LLM 挂了退抽取式、核验失败退原文摘录 |
